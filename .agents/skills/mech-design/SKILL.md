---
name: mech-design
description: Create Heavy Rig chassis baseline images and derive visually consistent weapon variants using the repository design kit and current gameplay mounts. Use for mech image design, not gameplay balance or production model replacement.
---

Read `design/mechs/README.md` from the repository root, then the selected chassis's `design/mechs/chassis/<id>/design.json` if present. Run the kit against the current checkout; never copy a stale mount list from chat history.

When `design.json` names a shared-master record, verify its approved artifact hashes before deriving 3D work. Preserve approved sources, create new revisions for motion or geometry changes, and do not infer motion/gameplay acceptance from visual approval.

For work beyond image generation, read `design/mechs/asset-production.md` and apply the web-3D asset pipeline skill. Preserve raw model exports, record assembly mappings and pivots, and distinguish diagnostic articulation from validated game-ready assets. Update the process with observed failures and repairs; do not promote untested segmentation or polygon budgets to defaults.

For a new baseline, use its A variant with a fully fitted, legal representative loadout unless the owner specifies otherwise. Compose with `bun run mech:prompt <request.json> <output-directory>`. Read the emitted prompt and mount checklist. Generate with the available image-generation skill/tool. Save the exact request, prompt, generated PNG, and mount review in a new versioned draft directory. Do not overwrite approved artwork. If the image tool is unavailable, report the limitation; do not substitute a diagram or silently use another provider.

When a 3D chassis master exists, follow the modular consistency rules in `design/mechs/asset-production.md`: assemble variants from the exact shared body and interchangeable modules, render approval views from that assembly, and generate only missing components. Do not send a complete variant back through image-to-3D generation unless the owner explicitly approves a new chassis or structural exception. Keep the master provisional until approved; record source/module hashes and verify shared geometry in exports.

For a concept-image variant before a 3D master exists, require an explicitly owner-approved baseline and its actual image. The composer refuses draft, wrong-chassis or stale-contract baselines. Inspect the baseline, pass its PNG to the image tool as the edit target, and use the emitted variant-edit prompt. Keep the shared chassis unchanged; apply only the listed module changes and explicitly allowed structural exceptions. Derive every variant directly from the same approved baseline, never from another variant.

Inspect the generated image, not merely its prompt. Count mount assemblies (a pod or barrel array is one mount), verify own-left/own-right families, positions and empty interfaces, and check for added weapons and chassis drift. Mark occluded or ambiguous mounts uncertain; do not claim they pass. Repair concrete defects before presenting a candidate. Report the mount checklist separately from the owner's aesthetic approval.

Baseline approval and each variant's approval are separate owner decisions. Approval is never inferred from generation, an agent review or silence. Record the owner's explicit approval and exact image hash before changing the active baseline. A new baseline makes derivatives of an older baseline stale. Creating art does not authorize replacing gameplay assets. Honor the current session's commit policy.

Before 3D generation, derive a front/back/own-left/own-right turnaround from the approved 3/4 concept. Read the turnaround section in `design/mechs/README.md`. Save four separate PNGs and exact prompts as a new draft; retain baseline image/hash and current gameplay contract. Review the views together for matching pose, proportions, weapon families and physical connections, including arms to torso, pod brackets, waist, hips, knees and ankles. Occlusion is expected in profile; do not invent extra mounts to expose hidden equipment. Correct contradictions, then obtain explicit owner approval of the complete view set before uploading it to Tripo. Concept approval does not approve unseen surfaces or turnarounds. Keep variants tied to the same chassis and corresponding approved views; reuse the 3D chassis with interchangeable weapon modules where possible. Model generation/uploads may be public per owner authorization; do not infer approval to publish unrelated material.
